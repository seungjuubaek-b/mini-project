# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 학원 공지 검색 서비스

**한 문장 설명:** 수강생이 키워드로 공지 검색을 요청하면, 공지 검색 API는 모의 검색 서비스를 조회하고 관련 가상 공지의 ID·제목·본문 목록과 결과 건수를 반환한다.

**정상 실행 흐름:**

```text
수강생 → 키워드 검색 요청 → 공지 검색 API → 모의 검색 서비스 → 관련 공지 목록
```

검색은 앞뒤 공백 제거 후 제목·본문의 부분 문자열 일치로 수행하며 영문 대소문자를 구분하지 않는다. 빈 입력은 입력 오류, 일치 없음은 정상 빈 목록, 검색 장애는 일시 실패로 구분한다.

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 모의 검색 서비스 | 고정 가상 공지 검색 | 검색 실패·응답 지연 | 전체 모의 구현, 실제 학원 연동 없음 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 수강생이 수료 기준 등 필요한 공지를 찾지 못하거나 결과를 기다린다.
- 복구 중에는 일시 실패 안내를 받고, 복구 후 검색을 다시 요청한다.

### 운영 영향

- 오류·실행 상태 확인, 제한된 재시도 또는 모의 서비스 재시작이 필요하다.
- 실제 검색 결과로 정상화를 확인하고 지속 장애를 판단해야 한다.

### 데이터·비용·보안 영향

- 가상 공지 조회만 제공하며 원본 공지 변경·삭제는 허용하지 않는다.
- 개인정보·외부 유료 API·AWS 자원 생성은 범위 밖이다. 로컬 실행으로 범위를 제한한다.

### 심각도

- [ ] 낮음
- [x] 중간
- [ ] 높음

**선택 근거:** 핵심 조회 요청이 실패하고 운영자 대응이 필요하지만 실제 데이터 변경·결제는 없다.

# 2. 에이전트 설계

아래는 개념적 책임 구분이다. 별도 LLM 에이전트·프로세스 수를 확정하지 않는다. 고정 정책에는 규칙과 상태 관리로 충분하며 LLM은 필수가 아니다.

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor

**관찰 데이터:** 기준 검색 응답·오류·응답시간. 중단 여부는 Diagnosis가 대상 실행 상태와 함께 확인한다.

**장애 판정 조건:** 5xx 응답, 2초 호출 한도 초과, 연결 실패 관찰 시 사건 생성. 직전 점검 종료 1초 후 다음 점검을 시작하며 주입 후 5초 이내 탐지를 목표로 한다.

**출력 메시지:** 사건 ID·추적 ID·대상·관찰 시각·증거. 동일 대상의 활성 사건은 하나로 병합한다.

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis

**입력:** 사건, 검색 오류·지연 증거, 모의 검색 서비스 실행 상태.

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| HTTP_5XX | 검색 오류 | 의존 서비스 5xx 응답 | 응답 근거로 분류, 일시성은 재시도 결과로 확인 |
| TIMEOUT | 응답 지연 | 호출 2초 초과 | 타임아웃으로 분류, 원인까지 단정하지 않음 |
| SERVICE_STOPPED | 대상 중단 | 연결 실패와 지정 컨테이너 중단 상태 | 두 근거가 모두 있어야 재시작 허용 |
| UNKNOWN | 원인 불명 | 연결 실패이나 실행 중 또는 상태 확인 불가 | 자동 변경 금지 |

**원인을 판단할 수 없을 때 행동:** 회로를 열고 자동 복구를 중단하며 근거와 함께 운영자에게 전달한다.

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery

**허용된 복구 행동:** 최초 실패 이후 최대 2회의 조회 재시도, 중단이 확인된 지정 모의 검색 컨테이너의 사건당 최대 1회 재시작.

**금지된 행동:** 임의 명령, 대상 밖 서비스 조작, 공지 변경·삭제, 인증정보 변경, AWS 자원 생성·확장, 장애 주입 스위치를 끄고 복구 성공으로 간주하는 행위.

**필요한 도구·API·명령:** 검색 조회 기능과 지정 대상 상태 조회·재시작 기능만 필요하다. 구체 명령·구현 코드는 정의하지 않는다.

**실패 시 행동:** 시도 결과 기록 후 Orchestrator로 제어를 반환한다.

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification

**독립성이 필요한 이유:** 재시작이나 복구 조회의 성공만으로 사용자 검색 결과의 정확성을 보장할 수 없다.

**검증 항목:** 실제 검색 API를 통한 기준 검색 2회 연속 성공, 각 2초 이내 응답, 공지 ID·제목·본문·건수 기대값 일치. 실험 전후 원본 공지 동일성은 별도 확인한다.

**복구 실패 판정 조건:** 오류·시간 초과·결과 불일치 중 하나라도 발생하면 미복구다. Recovery 보고만으로 완료 처리하지 않는다.

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 역할 호출 순서와 사건 상태, 재시도·시간 한도, 반복 장애를 일관되게 관리해야 한다.

### 오케스트레이터의 책임

- 사건 생성·병합과 역할 호출, 횟수·시간 기록.
- 독립 검증에 따른 완료 판정, 회로 차단과 운영자 전달.
- 제어부 재실행 시 진행 중 사건을 운영자 확인 대상으로 전환.

### 오케스트레이터가 해서는 안 되는 일

- 횟수·시간·권한 제한 우회 또는 복구 도구 직접 조작.
- 검증 실패를 성공으로 변경하거나 사람의 재개 요청을 자동 승인.

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---|
| Monitor | 기준 검색 응답·시간 | 사건·탐지 근거 | 정기 관찰 흐름 | 조회·사건 생성 | 검색 2초 |
| Diagnosis | 사건·실행 상태 | 분류·근거·복구안 | Orchestrator | 증거 읽기 | 사건 전체 한도 내 |
| Recovery | 승인 정책·잔여 한도 | 시도·결과 | Orchestrator | 제한 조회·지정 대상 재시작 | 조회당 2초, 재시작 준비 대기 최대 10초, 사건 한도 적용 |
| Verification | 기준 검색·기대값 | 독립 성공·실패 | Orchestrator | 검색 API 조회 | 검색당 2초, 총 2회 |
| Notification | 상태·근거·이력 | 화면·로그 결과 | Orchestrator | 결과 표시 | 별도 외부 전송 대기 없음 |
| Orchestrator | 사건·역할 결과 | 상태·중단·전달 | 사건 처리 흐름 | 호출·한도 관리 | 탐지부터 25초 |

### 협업 흐름

```text
장애 발생 → Monitor → Diagnosis → 한도·권한 확인 → Recovery → Verification
  ├─ 검증 성공 → 복구 완료·이력 표시
  ├─ 실패·잔여 한도 있음 → 허용 정책 내 다음 시도
  └─ 한도 소진·원인 불명·시간 초과 → 회로 열림·운영자 전달
```

중단 사건에서 재시작 후 HTTP 오류가 발생해도 다른 복구 전략을 추가하지 않는다. 복구 중 일반 사용자 요청은 일시 실패를 반환하고 완료 후 재검색하도록 한다.

# 3. 자율성과 통제

## 3.1 자동으로 실행해도 되는 복구는 무엇인가?

| 복구 행동 | 자동 허용 이유 | 영향 범위 | 선행조건 | 실행 후 검증 |
|---|---|---|---|---|
| 조회 재시도 | 원본을 변경하지 않음 | 모의 검색 조회 | 회로 닫힘, 시도·시간 잔여 | 독립 검색 2회 |
| 지정 컨테이너 재시작 | 격리된 실습 대상 복원 | 모의 검색 서비스 하나 | 중단 확인, 재시작 미시도, 시간 잔여 | 준비 상태 후 독립 검색 2회 |

## 3.2 사람의 승인이 필요한 복구는 무엇인가?

| 복구 행동 | 승인 필요 이유 | 승인자 | 승인 타임아웃 | 미승인 시 행동 |
|---|---|---|---|---|
| 회로 재개 | 반복·지속 장애 원인 확인 필요 | 실습 운영자, 개인 배정 [미결정] | 자동 승인 없음 | 열린 상태 유지 |
| 정책 변경 | 영향·한도 재검토 필요 | 사용자·개발팀 | 자동 승인 없음 | 기존 정책 유지, 별도 검토 |

한도 소진 후 원인 조사는 사람이 담당한다. 운영자 전달은 로컬 상태 조회와 로그 표시로 제공하며 외부 메신저·메일은 사용하지 않는다.

## 3.3 복구를 몇 번까지 재시도할 것인가?

**최대 시도 횟수:** 조회는 최초 실패 이후 복구 조회 최대 2회, 재시작은 사건당 1회. 검증 조회는 복구 시도와 구분해 2회 수행하며 한도 초기화 근거로 사용하지 않는다.

**대기 방식·대기시간:** 조회 재시도 전 각각 1초·2초 대기하는 제한된 지수 백오프. 재시작 후 준비 대기는 최대 10초.

**시도 횟수를 저장할 위치:** 사건·회로 상태와 함께 로컬 영속 저장. 구체 저장 기술은 상세 설계에서 결정한다.

## 3.4 무한 복구 루프를 어떻게 방지할 것인가?

- 사건별 시도 상한과 탐지 후 25초의 전체 처리 한도.
- 동일 대상 활성 사건 병합, 시도 전 횟수 기록, 제어부 재실행 시 자동 조치 재개 금지.
- 회로 차단·냉각·수동 재개, 실패 이력과 근거의 운영자 전달.

**회로 차단 조건:** 한도 소진·원인 불명·전체 시간 초과 시 즉시 열림. 또는 60초 내 같은 의존 서비스에서 별도 사건 3건 발생 시 열림.

**회로 재개 조건:** 최소 30초 냉각 후 운영자의 명시적 재개 요청과 독립 검색 2회 통과. 실패하면 열린 상태 유지. 재개 후 반복 사건 집계는 새로 시작한다.

열린 동안 자동 복구·일반 검색·정기 검색 점검의 의존 호출을 중단한다. 상태 조회와 운영자 요청에 따른 재개 검증은 허용한다.

## 3.5 잘못된 복구를 어떻게 취소할 것인가?

| 복구 행동 | 변경 전 저장할 상태 | 실패 판정 | 롤백 방법 | 롤백 검증 |
|---|---|---|---|---|
| 검색 재시도 | 사건·시도 횟수, 원본은 변경 없음 | 오류·지연·검증 실패 | 데이터 롤백 불필요, 추가 호출 중단 | 한도 초과 호출 없음·원본 동일 |
| 컨테이너 재시작 | 대상 식별·실행 상태·시도 기록 | 준비 실패·검증 실패 | 원본 보존, 추가 재시작 중단 및 운영자 전달 | 최종 상태·원본 동일성 확인 |

진행 중 재시작이 전체 시간 한도에 도달하면 추가 변경 없이 최종 상태를 확인하고 운영자에게 전달한다. 운영 설정·데이터 변경은 복구 정책에 포함하지 않는다.

# 5. 검증

## 5.1 복구 성공을 어떤 지표로 판정할 것인가?

| 지표 | 정상 기준 | 측정 위치 | 실패 기준 |
|---|---|---|---|
| 상태·기능 점검 | 사용자 검색 경로로 기대 공지 반환 | Monitor·Verification | 상태 응답만 정상이고 결과 불일치 |
| 정상 시 오탐 | 정상 기준 검색 10회에서 사건 0건 | 사건 이력 | 잘못된 사건 발생 |
| 응답시간 | 검증 검색 2회 각각 2초 이내 | Verification | 한 번이라도 시간 초과 |
| 핵심 검색 기능 | ID·제목·본문·건수 기대값 일치 | Verification | 오류·불일치 |
| 회귀 확인 | 정상·빈 목록·빈 입력 구분 유지 | 후속 검증 | 구분 실패 |
| 데이터 무결성 | 실험 전후 원본 동일 | 실험 전후 비교 | 원본 변경 |
| 복구 성공·시간 | 복구 가능한 세 장애 각 3회 모두 통과, 주입 후 30초 이내 | 실험·사건 이력 | 실패·시간 초과 |

오류율의 별도 운영 임계치는 MVP에 두지 않는다. 지속 장애는 정상화 성공률이 아니라 한도 준수·중단·전달 여부로 평가한다. 오늘은 검증 방법만 정의하며 테스트나 장애 실험을 실행하지 않는다.

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at = 실험 제어에서 장애를 활성화한 시각
detected_at = Monitor가 사건을 생성한 시각
recovery_started_at = 첫 복구 조치를 시작한 시각
recovered_at = 독립 검증 두 번째 검색이 통과한 시각

MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
검증 완료까지의 복구 처리시간 = recovered_at - recovery_started_at
```

MTTD·MTTR는 사건별 값과 평균을 함께 보고한다. 미복구 사건에는 recovered_at을 넣지 않으며 실패 수를 별도로 표시한다.

**시간을 기록할 컴포넌트:** 실험 제어·Monitor·Recovery·Verification의 이벤트를 Orchestrator가 사건별로 연결한다.

**시간 형식과 타임존:** UTC ISO 8601 저장, 화면은 Asia/Seoul 표시. 경과시간은 단조 증가 시간으로 계산한다.

## 5.3 어떤 로그를 반드시 보존할 것인가?

- 사건 ID, 추적 ID, 실험 ID, 대상 서비스.
- 주입·탐지·복구 시작·검증 완료 시각.
- 탐지·진단 근거, 선택 전략, 허용 대상 등 조치 인자, 실행 결과.
- 시도 횟수·대기시간, 검증 응답시간·기대값 일치 여부.
- 회로 상태, 운영자 재개 요청·결과, 최종 상태와 운영자 전달 정보.

**로그 저장 위치:** 로컬 영속 저장. 구현 기술은 상세 설계에서 결정한다.

**민감정보 제거 방법:** 원문 검색어 대신 실험 키워드 식별자를 기록한다. 개인정보·비밀키·환경 변수는 수집하지 않는다.

**로그 보존 기간:** 실습 검토용 7일, 이후 운영자가 삭제 가능.

저장 실패 시 추가 자동 변경을 중단하고 오류 상태를 노출한다.

## 5.4 최종 데모에서 어떤 장애를 주입할 것인가?

| 순서 | 장애 | 주입 방법 | 예상 탐지 | 예상 복구 | 성공 증거 |
|---|---|---|---|---|---|
| 1 | 정상 기준선 | 고정 공지 검색 | 정상 | 불필요 | 기대 결과, 정상 10회 오탐 0건 |
| 2 | 일시적 5xx | 실험 검색 최초 1회 503 | 오류 응답 | 제한 재시도 | 독립 검색·시간·시도 이력 |
| 3 | 타임아웃 | 실험 검색 최초 1회 3초 지연 | 2초 한도 초과 | 제한 재시도 | 독립 검색·시간·시도 이력 |

복구 가능한 세 장애는 각각 3회 반복한다. 매번 정상 상태에서 시작하며 성공률 실험과 60초 내 반복 장애 실험을 분리한다. 실행 중 연결 실패의 오진 방지와 정상 응답의 오답 검증도 확인한다. 일시 장애 종료는 사전에 정한 조건이며 복구 역할이 주입 모드를 끄지 않는다.
