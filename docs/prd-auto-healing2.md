- 서비스 선정: 사용자 승인 완료

- 근거: 대화에서 승인된 서비스 범위, 실습 가이드, 워크시트 템플릿, PRD 작성 지침
- 관련 워크시트: [학원 공지 검색 아이디에이션 워크시트](ideation-worksheet.md). 서비스 선정 결과와 정책을 정리하며 이 PRD와 함께 검토한다. 이전 재고 조회 워크시트는 이 PRD의 근거로 사용하지 않는다.

사용자는 서비스와 세 가지 장애 대응 범위를 승인했으며, 나머지 설계는 작성자에게 위임했다. 아래 수치와 통제 정책은 그 위임에 따라 정한 초안 기준이며 실제 성능 측정값이 아니다. 실제 운영 경험은 확인되지 않았다.

## 2. 프로젝트 개요

수강생이 키워드로 공지 검색을 요청하면, 공지 검색 API는 모의 검색 서비스를 호출하고 관련 가상 공지의 제목과 본문 목록을 반환한다.

```text
수강생 → 키워드 검색 요청 → 공지 검색 API → 모의 검색 서비스 → 관련 공지 목록
```

3일 MVP에서 검색 기능과 의존 서비스 장애에 대한 탐지·진단·제한된 복구·독립 검증을 보여준다. 오늘은 PRD 작성과 검토만 수행한다.

## 3. 문제 정의

검색 서비스가 오류를 반환하거나 지연·중단되면 수강생은 필요한 공지를 찾지 못한다. 운영자는 오류와 서비스 상태를 확인하고 재시도 또는 재시작한 뒤 검색 결과를 다시 확인해야 한다.

위 수동 흐름은 비교를 위한 가상 기준이며 학원의 실제 운영 절차를 조사한 결과가 아니다. 실제 수동 대응 시간과 개선율은 주장하지 않는다. 심각도는 일부 핵심 조회 기능이 중단되고 운영자 대응이 필요하다는 의미에서 중간으로 정한다.

조회만 제공하므로 복구 과정에서 공지 내용이 변경되어서는 안 된다. 재시도는 일시적 장애를 넘기는 수단이며 지속 장애 자체를 해결한다고 간주하지 않는다.

특정 개인의 역할 배정과 팀명은 미결정이며 핵심 요구사항 작성을 막지 않는다.

## 5. 목표와 성공 기준

| 목표 | 인수 기준 |
|---|---|
| 정상 검색 | 고정된 가상 공지에서 키워드에 대응하는 공지 ID·제목·본문이 기대값과 일치 |
| 장애 탐지 | 세 가지 장애별 실험에서 주입 후 5초 이내 사건 생성 |
| 자동 정상화 | 아래에 정한 복구 가능한 조건의 세 장애를 각각 3회 반복하고 모두 독립 검증 통과 |
| 기능 정상화 확인 | 검색 API를 통한 기준 검색이 2회 연속, 각 2초 이내 기대 결과 반환 |
| 복구 시간 | 복구 가능한 실험에서 장애 주입부터 검증 완료까지 30초 이내 |
| 실패 통제 | 지속 장애에서 한도 초과 조치 0회, 자동 조치 중단과 운영자 전달 기록 존재 |
| 데이터 보존 | 실험 전후 가상 공지 원본이 동일 |

시간 목표는 소규모 로컬 실습의 인수 기준이다. 실제 달성 여부는 이후 실험에서 확인한다. 평균 지표 외에 실험별 시간도 보존한다.

## 6. 비목표

- 실제 학원 시스템·개인정보·외부 유료 API 연동

- 임의 명령 생성·실행, 제한 없는 자동 복구

## 7. 정상 서비스 시나리오

1. 수강생이 FastAPI 기본 API 문서 화면에서 키워드를 입력한다.
2. 공지 검색 API가 입력을 확인하고 모의 검색 서비스에 조회한다.
3. 모의 검색 서비스가 고정 가상 공지의 제목·본문에서 키워드를 검색한다.
4. 공지 검색 API가 공지 ID·제목·본문 목록과 결과 건수를 반환한다.

검색은 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않는 부분 문자열 일치로 정의한다. 빈 키워드는 입력 오류로 처리한다. 일치 항목이 없으면 정상적인 빈 목록을 반환한다. 빈 결과와 의존 서비스 장애를 동일하게 표시하지 않는다.

## 8. 장애 시나리오

| 장애 | 위치와 신호 | 안전한 재현 조건 | 영향과 복구 방향 |
|---|---|---|---|
| HTTP 5xx | 모의 검색 서비스 오류 응답 | 지정된 실험 검색에 최초 1회 503 반환 후 정상 동작 | 조회 실패, 대기 후 제한된 재시도 |
| 응답 지연 | 의존 서비스 호출 2초 초과 | 지정된 실험 검색에 최초 1회 3초 지연 후 정상 동작 | 대기·타임아웃, 제한된 재시도 |
| 프로세스 중단 | 연결 실패 및 관리 상태의 중단 확인 | 로컬 모의 검색 컨테이너만 중단 | 검색 불가, 확인된 대상 재시작 |
| 지속 장애 | 재시도 또는 검증 계속 실패 | 모든 검색에 503 반환 | 자동 조치 중단과 운영자 전달 |
| 반복 장애 | 동일 의존 서비스의 사건 반복 | 사건 종료 후 짧은 간격으로 장애 재발 | 회로 차단 및 수동 재개 |

지연·오류의 일회성 종료는 일시 장애의 재현 조건이며 Recovery가 주입 스위치를 끄는 행위를 복구 성과로 계산하지 않는다. 프로세스 중단은 실제 허용 대상 재시작으로 복원한다. 연결 실패만으로 중단을 단정하지 않는다.

## 9. 멀티 에이전트 구성

다음은 책임을 구분하는 개념적 역할이다. 모든 역할을 독립 LLM 에이전트나 프로세스로 만들 필요는 없다. 고정된 장애와 복구 정책에는 규칙과 상태 관리로 충분하며 MVP에 LLM은 필수로 두지 않는다.

| 역할 | 책임·입력 | 출력 | 정보·허용 행동 | 금지 행동 | 실패 시 행동 |
|---|---|---|---|---|---|
| Monitor | 1초 주기 검색 상태 점검, 오류·지연 관찰 | 사건과 탐지 근거 | 검색 응답·시간 조회, 사건 생성 | 복구·설정 변경 | 관찰 실패를 기록하고 Orchestrator에 전달 |
| Diagnosis | 사건과 상태 증거로 유형 분류 | 유형·근거·허용 복구안 | 응답·실행 상태 읽기 | 복구 직접 실행, 연결 실패만으로 중단 확정 | 원인 불명으로 운영자 전달 |
| Recovery | 승인된 정책과 사건을 받아 조치 | 시도 내역·결과 | 제한된 조회 재시도, 지정 컨테이너 재시작 | 임의 명령, 원본 공지 변경, 타 대상 조작 | 실패 기록 후 제어 반환 |
| Verification | 복구 결과와 기준 검색을 받아 기능 확인 | 독립 성공·실패와 근거 | 검색 API 조회, 기대값 비교 | Recovery 보고만으로 성공 판정 | 미복구로 판정 |
| Orchestrator | 사건 상태·역할 호출·한도 관리 | 상태 전이·중단·전달 | 역할 호출, 횟수·시간 관리 | 한도 우회, 직접 서비스 조작 | 추가 조치 중단 및 실패 기록 |
| Notification | 최종 상태와 증거 전달 | 화면·로그의 운영자 확인 정보 | 결과·권고 표시 | 복구 정책 변경 | 전달 실패 기록, 조회 가능한 이력 보존 |

Verification은 Recovery의 성공 보고와 별도로 실제 사용자 경로를 조회한다. 상태·시도·중단 정책을 일관되게 적용하기 위해 Orchestrator 책임을 둔다. Notification은 별도 외부 메시징 서비스 없이 상태 조회와 로그 표시로 충족한다.

## 10. 에이전트 협업 흐름

```text
상태 관찰 → 사건 생성 → 진단 → 허용 여부·한도 확인 → 제한된 복구
→ 독립 검증 → 성공이면 복구 완료 기록
             → 실패이면 남은 정책 한도 내 다음 시도
             → 한도 소진·원인 불명·전체 시간 초과이면 중단 및 운영자 전달
```

동일 의존 서비스에 활성 사건은 하나만 유지하고 추가 관찰은 해당 사건에 합친다. 사건 ID와 원래 요청의 추적 ID를 연결한다. 복구 진행 중 사용자 요청은 빠르게 일시 장애 결과를 받고, 완료 후 다시 검색한다. 원래 사용자 요청을 30초 동안 붙잡아 두지 않는다.

## 11. 장애별 복구정책

| 장애 | 탐지·진단 근거 | 1차 복구 | 후속 복구 | 최대 시도 | 사람 승인 | 롤백·안전 중단 | 성공 검증 |
|---|---|---|---|---|---|---|---|
| 5xx | 의존 서비스의 5xx 응답 | 1초 후 조회 재시도 | 실패 시 2초 후 마지막 조회 재시도 | 최초 실패 이후 복구 조회 2회 | 한도 내 불필요 | 조회 변경 없음, 한도 후 중단 | 독립 기준 검색 2회 |
| 타임아웃 | 호출 제한 2초 초과 | 1초 후 조회 재시도 | 실패 시 2초 후 마지막 조회 재시도 | 최초 실패 이후 복구 조회 2회 | 한도 내 불필요 | 지연 요청 결과를 성공으로 뒤늦게 반영하지 않음 | 독립 기준 검색 2회 |
| 컨테이너 중단 | 연결 실패와 지정 대상 중단 상태 | 지정 컨테이너 재시작 | 준비 완료를 최대 10초 기다린 뒤 검증 | 재시작 1회 | 한도 내 불필요 | 공지 원본 보존, 실패 시 추가 재시작 금지 | 독립 기준 검색 2회 |

복구 조회가 성공하면 Verification을 수행한다. 검증이 실패해도 이미 수행한 복구 시도는 차감된 상태로 유지한다. 검증 조회는 각 2초 제한으로 2회 수행하고 별도 집계하며, 그 자체가 추가 Recovery를 무한히 유발해서는 안 된다. 중단 사건에서 HTTP 오류가 나타나도 다른 복구 전략을 추가하지 않고 미복구로 넘긴다.

- Monitor는 직전 점검 종료 후 1초 뒤 다음 점검을 시작하고, 점검 요청 한도는 2초다. 정상 상태의 연속 점검 간격과 제한시간을 고려해 탐지 목표를 5초로 정한다.
- 전체 사건 처리 한도는 탐지 시점부터 25초다. 시간 소진 시 새 조치를 시작하지 않는다. 진행 중 재시작은 추가 변경 없이 최종 상태를 확인하고 운영자에게 전달한다.
- 한도 소진·원인 불명·전체 시간 초과 시 즉시 해당 의존 서비스 회로를 연다. 또한 60초 내 별도 사건이 3건 발생하면 반복 장애로 회로를 연다.
- 회로가 열린 동안 자동 복구와 업무 검색의 의존 서비스 호출을 중단한다. 상태 조회는 가능하다.
- 최소 30초 냉각 후 운영자가 명시적으로 재개할 수 있다. 재개 전 독립 기준 검색 2회가 통과해야 하며 실패하면 열린 상태를 유지한다. 재개 후 반복 사건 집계는 새로 시작한다.
- 시도·회로·사건 상태는 실행 간 보존한다. 제어부 재실행 시 진행 중 사건은 자동 조치를 이어가지 않고 운영자 확인 대상으로 전환한다.

## 12. 자율성과 Human-in-the-loop

| 구분 | 행동 |
|---|---|
| 자동 실행 가능 | 상태 읽기, 사건 생성, 정해진 조회 재시도, 중단 확인된 모의 검색 컨테이너의 1회 재시작, 독립 검증, 결과 기록 |
| 사람 판단·승인 필요 | 회로 재개, 제한 소진 후 수동 원인 조사, 실행 중 복구 정책 변경 |
| 자동 실행 금지 | 임의 쉘 명령, 허용 대상 밖 재시작, 공지 데이터 변경·삭제, 인증정보 변경, AWS 자원 생성·확장 |

정책 변경은 자동 복구 기능에 포함하지 않는다. 운영자가 검토한 뒤 별도로 반영한다. 사람의 재개 요청이 없으면 계속 열린 상태를 유지하고 자동 승인하지 않는다. 외부 이메일·메신저 전송은 범위 밖이다.

## 13. 기능 요구사항

### FR-001 키워드 검색
- 설명: 가상 공지의 제목·본문 검색을 제공한다.
- 입력: 키워드.
- 기대 동작: 모의 검색 서비스의 검색 결과 반환.
- 예외 상황: 빈 입력은 입력 오류, 일치 없음은 빈 목록, 장애는 명시적 일시 실패로 구분.
- 인수조건: 기준 키워드의 공지 ID·제목·본문·건수가 기대값과 일치하고 세 예외가 구분된다.

### FR-002 장애 관찰과 사건 생성
- 설명: 사용자 요청 유무와 관계없이 검색 경로를 점검한다.
- 입력: 기준 검색 응답·시간·오류.
- 기대 동작: 이상 관찰 시 사건과 근거 생성, 중복 사건 병합.
- 예외 상황: 회로가 열리면 정기 업무 검색을 중단한다.
- 인수조건: 장애별 탐지 5초 이내, 동일 의존 서비스의 동시 활성 사건은 최대 1건이다.

### FR-003 증거 기반 진단
- 설명: 오류·지연·중단을 구분한다.
- 입력: 사건과 의존 서비스 실행 상태.
- 기대 동작: 장애 분류 및 허용 복구 방향 결정.
- 예외 상황: 연결 실패에도 서비스가 실행 중이거나 상태를 확인할 수 없으면 원인 불명으로 전달.
- 인수조건: 중단 확인 없이 재시작하지 않으며 진단 근거를 기록한다.

### FR-004 제한된 복구
- 설명: 장애별 허용된 조치만 실행한다.
- 입력: 진단 결과와 잔여 횟수·시간.
- 기대 동작: 11절 정책 적용, 시도 전에 횟수 기록.
- 예외 상황: 한도 소진·중단 확인 불가·시간 초과는 안전 중단.
- 인수조건: 복구 조회 최대 2회, 재시작 최대 1회, 허용 범위 밖 조치 0회다.

### FR-005 독립 검증
- 설명: 실제 사용자 검색 기능의 정상화를 확인한다.
- 입력: 기준 키워드와 고정 기대 결과.
- 기대 동작: Recovery와 별도 단계에서 검색 API를 2회 조회한다.
- 예외 상황: 응답 성공이어도 결과 불일치·시간 초과는 실패.
- 인수조건: 2회 모두 각 2초 이내 기대값 일치 시에만 복구 완료로 기록한다.

### FR-006 회로 차단과 수동 재개
- 설명: 지속·반복 장애의 자동 조치를 제한한다.
- 입력: 실패 한도·반복 사건·냉각시간·운영자 재개 요청.
- 기대 동작: 11절의 열림·재개 정책 적용.
- 예외 상황: 냉각 미완료 또는 재개 검증 실패는 열린 상태 유지.
- 인수조건: 열린 동안 자동 복구 0회, 운영자 요청과 재개 검증 없이 회로를 닫지 않는다.

### FR-007 상태와 증거 조회
- 설명: 운영자가 사건과 결과를 확인한다.
- 입력: 사건 식별자 또는 상태 조회 요청.
- 기대 동작: 진단 근거·시도·검증·최종 상태·다음 판단 필요 여부 표시.
- 예외 상황: 저장에 실패하면 추가 자동 변경을 중단하고 오류 상태를 노출한다.
- 인수조건: 사건별 이력이 연결되어 조회되고 미복구가 성공으로 표시되지 않는다.

### FR-008 격리된 실험 지원
- 설명: 정해진 장애 조건과 반복 실험을 지원한다.
- 입력: 실습 운영자의 장애 유형 선택.
- 기대 동작: 모의 의존 서비스에만 영향, 실험별 주입 시각 기록.
- 예외 상황: 실험 종료 후 정상 모드 복원 및 서비스 상태 확인.
- 인수조건: 가상 공지 원본과 다른 서비스 상태를 변경하지 않고 동일 조건을 반복 가능하다.

## 14. 비기능 요구사항

- NFR-001 재현성: Windows 학원 노트북의 로컬 Docker 환경을 기준으로 한다. Python·FastAPI·Docker를 활용하고 AWS 경험은 보유 기술로만 기록한다. 구체 버전·설치 가능 여부는 이후 환경 확인 대상이다.
- NFR-002 안전성: 제어 가능한 대상은 지정 모의 검색 서비스 하나이며, 자동 조치는 고정된 허용 목록에서만 선택한다.
- NFR-003 관측 가능성: 모든 조치는 사건·추적 식별자와 근거·시간·결과로 설명 가능해야 한다.
- NFR-004 성능: 동시 사용자 성능 보장은 범위 밖이며 단일 실험 요청을 기준으로 검색 2초, 복구 가능한 사건 30초 목표를 검증한다.
- NFR-005 보안: 실습 화면과 제어 기능은 로컬에서만 접근한다. 가상 데이터만 사용하고 비밀키·개인정보를 로그에 남기지 않는다.
- NFR-006 신뢰성: 복구와 검증을 분리하고 상태 보존 불가 시 자동 조치를 멈춘다. 제어부 자체의 고가용성은 비목표다.

## 15. 데이터와 로그 요구사항

가상 공지는 공지 ID·제목·본문으로 구성한다. 기준 검색은 정답 공지가 있는 키워드, 결과가 없는 키워드, 빈 입력을 포함한다. 정확한 가상 문구는 이후 결정해도 되지만 실험 중에는 데이터와 기대값을 고정한다.

필수 기록은 사건 ID, 추적 ID, 대상 서비스, 실험 ID, 장애 주입 시각, 탐지 시각, 복구 시작 시각, 검증 완료 시각, 탐지·진단 근거, 조치 유형, 시도 횟수, 대기시간, 결과, 검증 응답시간·기대값 일치 여부, 회로 상태, 운영자 재개 요청, 최종 상태다.

시각은 UTC 기준 ISO 8601로 보존하고 화면은 Asia/Seoul로 표시한다. 경과시간은 단조 증가 시간 기준으로 계산한다. 최종 정상화 시각은 독립 검증 두 번째 검색이 통과한 시점이다. 실패 사건에는 정상화 시각을 넣지 않는다.

이력과 제어 상태는 로컬 영속 저장으로 보존하며 구현 방식은 상세 설계에 맡긴다. 실습 검토를 위해 7일 보존하고 이후 운영자가 삭제할 수 있다. 원문 검색어 대신 실험용 키워드 식별자를 기록하며 비밀키·호스트 환경 변수·개인정보는 수집하지 않는다.

## 16. 검증 및 완료 기준

오늘은 검증 방법만 정의하며 테스트 작성·실행이나 장애 주입을 수행하지 않는다.

| 시나리오 | 향후 확인할 증거 |
|---|---|
| 정상·빈 결과·빈 입력 | 기대 결과 및 예외 구분 |
| 일시적 503, 3회 반복 | 탐지·제한 재시도·독립 검증과 시간 기록 |
| 일회성 3초 지연, 3회 반복 | 2초 타임아웃·제한 재시도·독립 검증 |
| 모의 검색 컨테이너 중단, 3회 반복 | 중단 확인·재시작 1회 이내·독립 검증 |
| 지속 503 | 한도 후 중단·회로 열림·운영자 전달 |
| 60초 내 사건 3건 | 반복 장애 회로 차단, 냉각과 운영자 재개 통제 |
| 실행 중이나 연결 불가 | 원인 불명 처리, 불필요한 재시작 없음 |
| 정상 응답이지만 공지 결과 오답 | 검증 실패, 복구 완료 선언 없음 |

반복 실험은 이전 사건을 종료하고 독립 검증 후 정상 상태에서 시작한다. 성공률 평가용 독립 실험은 반복 장애 집계 구간과 분리한다. 반복 장애 검증만 의도적으로 60초 내 수행한다.

- MTTD = 탐지 시각 − 장애 주입 시각. 평균과 사건별 값을 함께 보고한다.
- MTTR = 검증 완료 시각 − 장애 주입 시각. 복구 성공 사건의 평균과 개별 값을 보고하고 실패 건수를 별도로 명시한다.
- 복구 성공률 = 독립 검증 통과 사건 수 ÷ 복구 가능 조건의 전체 실험 사건 수.
- 지속 장애는 자동 정상화 성공에 포함하지 않고 안전 중단의 성공 여부로 평가한다.
- 정상 기준 검색 10회에서 잘못된 사건 생성이 0건인지 확인한다.
- 데이터 원본 동일성, 시도 상한, 독립 검증, 시간 기록과 실패 전달이 모두 충족되어야 구현 완료로 판단한다.

## 17. 3일 MVP 포함·제외 범위

포함 범위는 키워드 검색, 모의 검색 의존 서비스, 오류·지연·중단의 세 장애, 역할별 복구 흐름, 독립 기능 검증, 회로 차단과 운영자 재개, 로컬 이력·시간 기록이다.

제외 범위는 6절의 기능과 실제 운영 환경이다. 오늘의 산출물은 학원 공지 검색 워크시트, 이 PRD 초안과 검토·승인 기록이다. 구현·검증·배포에 대한 개발 작업목록은 작성하지 않는다.
